## The full pipeline

!!! figure "Metrics and logs, from the app to your browser"
    ```mermaid

        end

        metrics --> prometheus["prometheus\n(scrapes /metrics every 15s)"]
        stdout --> dockerlog[("docker json-file\nlog driver")]
        dockerlog --> promtail["promtail\n(docker_sd_configs, filtered by\ncom.docker.compose.project label)"]
        promtail --> loki["loki\n(push API, :3100)"]
        prometheus --> grafana["grafana"]
        loki --> grafana

        linkStyle default stroke-width:3px,stroke:#333333
        style appnode stroke-width:1px,stroke:#333333
    ```

    > Two independent paths converge on Grafana. **Metrics:** `setup_metrics()` mounts `prometheus_fastapi_instrumentator` at `GET /metrics` (request counts, latency histograms, in-progress requests, namespaced by `APP_SERVICE_NAME`), plus one hand-written `Counter` — `app_unhandled_exceptions_total`, labeled by `exception_type`, incremented in `GlobalExceptionMiddleware` — and Prometheus (`observability/prometheus/prometheus.yml.template`, real file generated by `scripts/makefile/*_env.sh`) scrapes that endpoint every 15 seconds. **Logs:** every log line is a single JSON object on stdout (`APP_LOG_FORMAT=json`); Docker's own `json-file` log driver captures it; Promtail discovers the container via `docker_sd_configs` against the Docker socket, filtered to only this Compose project's containers (`com.docker.compose.project=${APP_SERVICE_NAME}` — so an unrelated project running Docker on the same host never leaks into this Loki instance), unwraps Docker's JSON log-line wrapper, then promotes just the `level` field to a Loki label (low-cardinality, 5 values) before pushing to Loki's `/loki/api/v1/push`. Grafana is provisioned (`observability/grafana/provisioning/datasources/datasources.yml`) with both Prometheus and Loki as datasources, and one dashboard (`app-overview.json`) ships pre-built: request rate by endpoint, 5xx error rate, p50/p95/p99 latency, unhandled exceptions by type, and a live-tailing logs panel — all queryable at `http://localhost:3000` (`admin`/`admin`).

This entire stack (`prometheus`/`grafana`/`loki`/`promtail`) sits behind the `development` Compose profile — same gating as Adminer — because neither Prometheus nor Loki has built-in authentication; even bound to `127.0.0.1`, that's not safe to run unattended on a production host. A real deployment's metrics/log collection is a separate, deliberately-secured decision, not this local stack (tracked in the [production readiness roadmap](https://github.com/ivan-borovets/fastapi-clean-example/blob/master/docs/plans/0-production-readiness-roadmap.md)).

## The 5xx email-alerting path

Separately from the metrics/logs pipeline above, `GlobalExceptionMiddleware` can also email an on-call address the moment a *genuine* unhandled server error occurs — never an ordinary mapped 4xx business/validation error, since those never reach this middleware at all (they're already resolved to their own response by `fastapi-error-map` before this catch-all runs).

!!! figure "Rate-limited alert email on an unhandled 5xx"
    ```mermaid
    %%{init: {"theme": "default", "themeVariables": {"fontSize": "14px"}, "flowchart": {"nodeSpacing": 20, "rankSpacing": 16, "padding": 10, "subGraphTitleMargin": {"top": 5, "bottom": 12}, "useMaxWidth": false}}}%%
    flowchart LR
        exc["unhandled exception reaches\nGlobalExceptionMiddleware"] --> logit["logger.exception(...)\n+ UNHANDLED_EXCEPTIONS_TOTAL.inc()"]
        logit --> gate{"ALERT_ENABLED\nAND cooldown.should_send(type)?"}
        gate -->|no| skip["no email --\nstill logged + counted"]
        gate -->|yes| build["build_error_alert_email()\n(subject, html_body)"]
        build --> send["EmailSender.send(...)"]
        send --> oncall["ALERT_TO_EMAILS\n/ CC / BCC"]

        linkStyle default stroke-width:3px,stroke:#333333
    ```

    > `AlertCooldown` (`alerting.py`) tracks the last-sent time **per exception type**, in a plain in-memory dict — so one exception type spiking during an outage can't silence alerts for an unrelated one, and `ALERT_COOLDOWN_S` (default `300` seconds) caps how often the *same* exception type can re-alert, keeping thousands of identical errors from flooding an inbox. The email itself carries the exception type, message, request path/method, client host, and — via `RequestUserContext`, a best-effort, three-state lookup (`authenticated`/`anonymous`/`unknown`, since resolving identity must never itself crash error handling) — who was making the request. Sending reuses the same `EmailSender` **port** (an abstract interface `core` declares without knowing which concrete adapter satisfies it — see [Layer Dependencies & Import Rules](../architecture/layer-dependencies.md)) as ordinary transactional email (see [Email (SMTP)](email.md)); `AlertSettings` is deliberately a separate settings class from `EmailSettings` since alerts go to operators about the system, not to end users about their account.

## `env.example`'s `ALERT_*` variables

| Variable | Default | Notes |
|---|---|---|
| `ALERT_ENABLED` | `false` | the master switch; everything above still logs/counts when this is off, it just never emails |
| `ALERT_TO_EMAILS` / `ALERT_CC_EMAILS` / `ALERT_BCC_EMAILS` | *(empty)* | comma-separated address lists, e.g. `oncall@yourdomain.com,backup@yourdomain.com` |
| `ALERT_COOLDOWN_S` | `300` | minimum seconds between two alert emails for the *same* exception type |
