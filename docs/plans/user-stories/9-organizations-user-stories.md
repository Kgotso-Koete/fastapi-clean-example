<tr style="background:#f2f2f2"><td colspan="9"><b>How to write the stories:</b> they come first, before the plan, which links to this file and never copies it. Each action is one row, in the order the actor takes it, with "As a, I want, so that" and its acceptance criteria. A promise not to do something is a story too; out-of-scope items are not (they go in the plan's "Deliberately out of scope" list). Each domain ends with a grey "No story here yet" row naming the actors it has no story for. Every story gets at least one human check that follows its journey and cites its ID, and the status columns are updated after each GREEN and before each commit.</td></tr>
<tr style="background:#f2f2f2"><td colspan="9"><b>Story terms are not code terms:</b> a story's <i>domain</i> is an area of the product as a person sees it, not a Domain-Driven Design domain or bounded context (this whole file sits in one bounded context, the Organizations module); a <i>journey</i> has no counterpart in the code; and an <i>action</i> is what an actor does, not a use case. The two map many to many: one use case can serve several actions (<code>RemoveOrganizationMember</code> serves revoking an invitation, removing a member and leaving), and one action can need several use cases. The <code>story</code> markers on the tests are what connect a story to the code that serves it.</td></tr>
<tr style="background:#f2f2f2"><td colspan="9"><b>Actors:</b> <b>US</b> user (anyone with an account; the row says when it's an invitee or an outsider); <b>OM</b> organization member (the row names the minimum role: Owner, Admin or Member); <b>IN</b> integrator (a developer's own server calling the public API with an API key); <b>SY</b> system (the software itself).</td></tr>
<tr style="background:#f2f2f2"><td colspan="9"><b>Status:</b> ✅ done, with where (plan step, human check or version); ⬜ not yet; <i>Partly</i> names what's done and what isn't. <b>Human checks</b> name the plan's "Human checks" subsection and the check numbers inside it.</td></tr>
<tr style="background:#f2f2f2"><td colspan="9"><b>Tests passing:</b> passed/run for each story, by kind of test: <b>BU</b> backend unit and <b>BI</b> backend integration (defined at the bottom). Counted, never typed: each test names its stories with a <code>story</code> marker, <code>tests/conftest.py</code> prints the counts at the end of every run, and these come from <code>make test-docker</code> on 2026-11-15. A kind a story should have but doesn't is marked as a gap.</td></tr>
<tr style="background:#f2f2f2"><td colspan="9"><b>Tests and stories:</b> tests mirror the code (one use case, entity, adapter or route each) and stories cut across it, so each test names the stories it proves with a <code>story</code> marker, and a story with no tests of a kind shows a gap. A few journey tests per domain walk a whole journey through the real stack, and each story's acceptance criteria are checked against its tests when the plan is written.</td></tr>
